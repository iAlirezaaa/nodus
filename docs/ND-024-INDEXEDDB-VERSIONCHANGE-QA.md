# ND-024 — IndexedDB versionchange closes stale connections (branch-only)

Date: 2026-11-18 18:35 UTC. **In progress** on `fix/nd-024-startup-storage-recovery`; **NOT released to original Site**.

## Problem and change

The separate optional Pages/local-first Nodus edition previously kept an IndexedDB connection open after a valid `indexedDB.open()`. A second tab upgrading or removing `nodus-pages-v1` could be blocked by the first tab, while the first retained an editor associated with old storage. The newly registered `connection.onversionchange` closes **that same handle**. Only when it is still the active `db` connection does the handler clear `db`, mark `state.localConflict=true`, retain `state.unsavedChanges=true`, and display Persian/English fail-closed save-status and a toast directing JSON export/reload. This prevents queued persistence from continuing with the stale connection. An obsolete handle cannot clear a newer connection, and a throwing `close()` does not unlock stale editing. No schema migration, document replacement, automatic backup write, animated-frame mutation or original authenticated Site change.

UI location: existing storage status and top notification after another tab upgrades IndexedDB; normal canvas/Details and **Export JSON** remain usable for preserving the in-memory draft. No additional button. The `getDB()` open-blocked/late-success recovery path remains covered by existing tests.
