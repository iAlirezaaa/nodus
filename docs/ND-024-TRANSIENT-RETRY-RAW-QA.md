# ND-024 — Preserve a raw recovery snapshot without enabling stale replacement

Date: 2026-11-18 17:33 UTC. **In progress (feature branch only); hosted Site release Blocked.**

## Problem and corrected behavior

In the optional **GitHub Pages local-first** Nodus edition—not the original authenticated ChatGPT Site—an initial failed IndexedDB read/validation may capture an invalid raw record for emergency JSON export. A later click on **Retry reading stored data / تلاش دوباره برای خواندن** could throw a transient blocked-open/read error. Previously the newer failure replaced the recovery object and discarded the captured raw snapshot, taking away the user's remaining emergency export option.

The changed `retryRecovery()` uses the newest *defined* corrupt raw record if available, but keeps an earlier captured snapshot when the new failure has no raw bytes. In the latter case it explicitly marks `storageRecovery.staleRaw=true`: this prior snapshot is **export-only**, never authoritative for replacing the current database. The recovery modal keeps **Download raw data / دانلود نسخهٔ خام** available and explains in Persian/English that a successful fresh read is required before replacement. `downloadRecovery()` on a stale snapshot **does not** acknowledge the recovery backup or unlock Import/Start fresh. `restoreLocalDocument()` and click handlers independently reject the stale source even if another control state is changed. A new valid read still exits recovery normally; a newly corrupt record resets stale status but keeps destructive controls locked until explicit current-record backup.

No local document, Undo/Redo, write transaction, schema, key, authenticated account, D1/R2 binding or shared room was migrated or modified by the fix. No new control is introduced. No animation frame writes were added. Old raw snapshots are only kept in temporary recovery state until reload.
